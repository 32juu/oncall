# Feature Specification: 告警认领与处置（Alert Claim & Disposition）

**Feature Branch**: `001-alert-claim`

**Created**: 2026-09-06

**Status**: Draft

**Input**: User description: 值班 SRE 在 AIOps 对一条告警完成诊断后可以认领该告警，建立「认领 → 归属 → 防重复接管 → 持久化」的责任闭环；抑制窗口与处置记录为同特性内的低优先级能力；v1 无账号体系，操作人以自报标识代替。

## User Scenarios & Testing

优先级 P1 → P3 递减；P1 单独即可作为可用 MVP。

### User Story 1 - 值班 SRE 认领一条已诊断告警（Priority: P1）

值班 SRE 在 AIOps 对某条告警完成诊断后，认领该告警表明「这条我来负责」。认领成功后该告警进入「处理中」，负责人与认领时间被记录，并对同班同事立即可见；此后同一条告警不能再被第二人接管——后续认领被拒绝，并被告知当前负责人是谁（先到先得、锁定到处理结束、无改派）。认领记录持久保存，服务重启后仍可完整查询。

**Why this priority**: 这是责任闭环的第一环，也是唯一能直接消除「多人对同一条告警重复处置」的机制；没有它，抑制（P2）与处置（P3）都无处附着。它是对「诊断完即结束」现状最短的价值补全。

**Independent Test**: 对一条未认领的已诊断告警，操作人 A 认领成功 → 操作人 B 认领同一告警被拒并看到负责人为 A → 重启服务后 A 的认领记录仍可查询。仅此即构成可用 MVP。

**Acceptance Scenarios**:

1. **Given** 一条已由 AIOps 诊断完成且未被认领的告警，**When** 值班 SRE 以操作人标识发起认领，**Then** 认领成功，该告警标记为「处理中」，负责人与认领时间被记录。
2. **Given** 该告警已被操作人 A 认领，**When** 操作人 B 尝试认领同一告警，**Then** 认领被拒绝，且 B 被告知当前负责人为 A。
3. **Given** 一条处于「处理中」的告警，**When** 同班同事查看该告警，**Then** 立即可见当前负责人与其认领时间。
4. **Given** 服务发生一次重启，**When** 重启后查询此前已认领的告警，**Then** 认领记录与状态仍完整可查。
5. **Given** 当前负责人 A 对同一告警再次发起认领，**When** 系统收到重复认领，**Then** 不产生第二个负责人，并明确提示该告警已由 A 本人负责。

---

### User Story 2 - 负责人为已认领告警设置抑制窗口（Priority: P2）

负责人可以为自己认领、仍在处理中的告警设置一段**到点自动失效**的静音期。静音期内该告警再次触发不再产生重复的诊断与打扰；到期后自动恢复正常行为。

**Why this priority**: 修复往往持续较久、告警可能反复触发；抑制能避免噪声掩盖真实的状态变化。但它是优化而非第一环，故降为 P2。

**Independent Test**: 认领告警 → 设 2 小时抑制窗口 → 期间同一告警再触发不产生新诊断/打扰 → 到点后恢复触发。可独立演示。

**Acceptance Scenarios**:

1. **Given** 当前负责人已认领某告警，**When** 为其设置一个结束时刻晚于当前时刻的抑制窗口，**Then** 窗口立即生效。
2. **Given** 抑制窗口生效中，**When** 同一条告警再次触发，**Then** 系统不产生新的诊断与打扰（必要记录保留）。
3. **Given** 抑制窗口已到结束时刻，**When** 该告警再次触发，**Then** 恢复正常触发/诊断行为。
4. **Given** 非负责人尝试为某已认领告警设置抑制窗口，**When** 发起操作，**Then** 被拒绝（仅当前负责人可操作）。
5. **Given** 传入的抑制窗口结束时刻早于/等于当前时刻，**When** 发起设置，**Then** 被拒绝并要求提供合法区间。

---

### User Story 3 - 负责人记录处置动作与结局（Priority: P3）

负责人可以为自己负责的告警记录实际处置动作与结局（如：已解决、误报、观察中），形成该告警从诊断到处置的完整时间线，作为事后复盘的依据。

**Why this priority**: 复盘与审计都依赖处置数据，但「记录」本身不产生即时保护价值，故为 P3。

**Independent Test**: 认领告警 → 记录处置动作并标记结局「已解决」 → 该告警进入结束态，历史时间线可完整读取。可独立演示。

**Acceptance Scenarios**:

1. **Given** 当前负责人已认领某告警，**When** 记录一条处置动作并标记结局为「已解决」，**Then** 该告警进入结束态且记录被保存。
2. **Given** 一条已认领告警已有处置记录，**When** 查看该告警，**Then** 能读到「诊断 → 认领 → 处置 → 结局」的完整时间线。
3. **Given** 非负责人尝试为某告警记录处置，**When** 发起操作，**Then** 被拒绝（仅当前负责人可操作）。
4. **Given** 负责人已将该告警标记为「已解决」，**When** 之后有操作人尝试认领，**Then** 认领被拒（告警已结束），与 P1 的排他规则一致。

---

### Edge Cases

- 认领一个不存在的告警标识、或一个尚未经过诊断的告警 → 认领被拒，提示该告警不存在或不可认领。
- 告警已处于结束态（已解决/已关闭）时收到认领 → 被拒并说明原因。
- 两个操作人几乎同时认领同一条告警 → 最终只允许一人成功，另一人收到拒绝与当前负责人。
- 操作人标识为空 → 认领被拒，提示必须提供操作人标识。
- 处理中告警在处置期间再次触发且被诊断为更高严重级别 → 抑制窗口（若存在）是否自动取消：默认**不**自动取消，抑制独立于级别变化（待 plan 阶段细化）。
- 冒名认领（A 冒用 B 的标识）→ v1 信任自报标识，属已知局限（见 Assumptions）。

## Requirements

### Functional Requirements

- **FR-001**: 系统必须允许值班 SRE 通过告警标识，对一条「已诊断且未认领」的告警执行认领。
- **FR-002**: 认领成功后，系统必须将该告警状态置为「处理中」，并记录负责人（操作人标识）与认领时间。
- **FR-003**: 系统必须让任何查看该告警的操作人能立即看到当前负责人与认领时间。
- **FR-004**: 系统必须拒绝对已认领告警的第二次认领，并返回当前负责人；负责人不得在告警进入结束态前变更（先到先得、无改派/移交）。
- **FR-005**: 系统必须持久保存认领记录与状态变化，服务重启后仍可完整查询。
- **FR-006**: 系统必须拒绝认领不存在或尚未完成诊断的告警（两者对认领是同一情形），以及已结束（已解决 / 已关闭）的告警，并给出可理解的提示。
- **FR-007**（P2）: 当前负责人必须能为一条处于「处理中」的告警设置带结束时刻的抑制窗口。
- **FR-008**（P2）: 抑制窗口生效期间，同一条告警再次触发不得产生重复的诊断/打扰；窗口到点后必须自动恢复正常行为。
- **FR-009**（P2）: 仅当前负责人能设置/管理抑制窗口；抑制窗口的结束时刻必须晚于当前时刻。
- **FR-010**（P3）: 当前负责人必须能为所负责的告警记录处置动作与结局。
- **FR-011**（P3）: 已结束的告警不可再被认领；认领与处置历史必须可完整回溯。

### Key Entities

- **告警（Alert）**: 被监控系统识别、并由 AIOps 完成一次诊断的异常事件；具有稳定标识与状态。诊断报告引用该告警。
- **认领/归属记录（Claim）**: 一条告警与「当前负责人 + 认领时间」的绑定；每条告警至多一个有效认领（v1 排他、无改派）。
- **告警状态（Alert Status）**: 生命周期状态：已诊断 → 处理中 → 已解决/已关闭。
- **抑制窗口（Suppression Window）**: 一条已认领告警的静音期定义（起止时刻），到点自动失效。
- **处置记录（Disposition）**: 负责人针对告警记录的动作描述与结局标签，构成完整时间线。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 100% 对「未认领」告警的认领动作成功，且负责人/认领时间立即可见。
- **SC-002**: 100% 对已认领告警的第二次认领被拒绝，且请求者被告知当前负责人。
- **SC-003**: 认领与状态记录在服务重启后 100% 可查询（零丢失）。
- **SC-004**: 值班 SRE 可在一次查询内确定任意一条已认领告警的当前负责人。
- **SC-005**（P2）: 抑制窗口在结束时刻自动失效，此后告警触发恢复正常，无需人工干预。
- **SC-006**（P3）: 已结束告警的「诊断 → 认领 → 处置 → 结局」时间线可完整读取，足以支撑复盘。

## Assumptions

- **操作人 = 自报字符串标识**（工号/姓名等）：系统信任该标识，不做认证、不建账号；冒名认领在 v1 属已知局限，由后续账号/权限体系解决。
- **每条告警有稳定标识**：认领与查询都挂在该标识上。当前 mock 告警需补充/暴露该标识，并保证 AIOps 诊断输出能关联回对应告警。
- 本功能叠加在现有 AIOps 诊断输出之上；诊断引擎本身不在本功能范围内改动。
- 认领功能只对「已完成一次 AIOps 诊断」的告警可见、可认领；从未被诊断的告警对认领而言等同未知告警——两者都不可认领、返回同一提示（FR-006）。
- 告警在认领视野内的状态演进只有：未认领（刚诊断完）→ 认领（处理中）→ 已解决 / 已关闭；「已结束」是已解决或已关闭的合称。
- 默认单值班团队场景，不做跨团队与多租户。
- 抑制窗口基于系统时钟计算失效；结束时刻由操作人提供并校验。

**范围边界（明确不做 / Out of Scope）**:

- 自动修复/自愈执行（高危执行类能力，属后续独立特性）。
- 接入真实监控/日志数据源（Prometheus、腾讯 CLS 等，属基础设施/独立特性）。
- 账号登录、角色与 RBAC 权限体系（后续切片，v1 以自报标识代替）。
- 改造 AIOps 诊断引擎本身的流程与模型。
- 复盘报告的自动生成（本功能只沉淀可复盘的数据，导出属后续特性）。
- 认领改派/移交（v1 先到先得、锁定到结束）。
